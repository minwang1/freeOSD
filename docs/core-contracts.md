# Core 契约审查决策

本文在平台 adapter 和功能页面并行开发前稳定 Core 边界。Core 契约描述跨平台业务语义；平台项目负责调用操作系统/显示器接口。这里的规则适用于 Windows 和 Linux，不代表每个平台都实现了每项能力。

## 身份与能力

- `MonitorId` 是当前发现会话内供调用定位设备的 ID，不携带 native handle，也不承诺重启后不变。
- `MonitorDescriptor` 提供可供 UI 展示、配置匹配的显示器元数据。持久化匹配不得仅依赖枚举序号；优先使用制造商/型号/序列号等可用信息，并为缺少序列号的设备保留人工确认策略。
- `MonitorCapabilities` 区分设备声明能力和探测能力。未声明但探测可读的 VCP 项必须保留 `probe-only` 语义；不能当成标准支持能力。
- 平台系统设置能力逐项表达“可查询/可修改”。HDR 可读取但不可写、刷新率可枚举但不可切换，都必须能独立表示。

## VCP 操作

- Core 使用原始 VCP code 和无符号数值；友好名称、OSD 状态名是可选元数据，不改变原始值。
- 写入接口只代表命令提交。需要验证的业务流程必须显式读回，不能把写入调用成功等同于显示器实际应用。
- 读写失败必须带机器可判断的错误类别（不支持、设备不可用/断开、访问受限、读取失败、写入失败、超时等）及适合日志的原始详情；UI 文案不从异常字符串反向解析类别。
- 同一显示器的硬件命令必须串行。Core 用例或 adapter 必须保证此不变量，并记录唯一责任方，避免双层死锁。

## 长任务、进度与取消

- 每个用例有唯一 `OperationId`；进度通知与结果都关联此 ID，通知不依赖 Avalonia dispatcher 或 UI 线程。
- 一个操作至多发出一个终态（成功、部分成功、失败或取消）。终态后不得继续发送普通进度。
- `CancellationToken` 表示用户希望停止后续工作；取消不得跳过安全恢复段。进入恢复阶段后必须完成恢复/有限重试，除非设备不可访问或进程被操作系统终止。
- 进度需表达阶段和当前对象；百分比可选，不能为了填百分比伪造精度。

## 显示模式试用与回滚

- 刷新率/显示模式变更是一项有时限的试用事务。Core 用例拥有试用状态、确认期限和确认/回滚决策；UI 仅展示倒计时并提交用户确认。
- Core 协调器在应用前生成唯一 trial ID 并传给 adapter；adapter 用该 ID 作为事务键，读取完整当前模式快照后应用请求模式，并返回旧模式和请求模式摘要。
- adapter 必须可用 trial ID 执行确认或恢复；恢复所需的完整平台数据由 adapter 持有/编码，不能只保存宽、高和整数 Hz。
- UI 消失、用户取消或确认期限届满时 Core 触发恢复。恢复失败是高优先级失败结果，必须保留重试/诊断信息。
- 确认和恢复是互斥的终态决定；同一决定可安全重试，反向决定返回 `InvalidState`。恢复失败必须保留事务快照供重试。
- 进程被强杀或操作系统崩溃时无法保证进程内计时器继续运行；不得声称覆盖此情形。若某平台能提供系统级回滚机制，可作为增强能力单独声明。

## 预设持久化

- 预设中 `VcpValues` 是唯一的 VCP 写入来源，键为原始 VCP code，值为原始值。识别控件的友好名称/OSD 标签属于控件配置元数据，不应在同一预设里再保存一份可能冲突的生效值。
- 可选刷新率和 HDR 值与 VCP 值分开保存；`null` 表示预设未请求该设置，不能解释为 HDR 关闭或默认刷新率。
- 采集时读不到的项目属于“采集结果/遗漏项”，不是用户期望应用的设置。保存流程返回 Capture Result，其中包含可保存的 Profile 和 omissions；不要把 omissions 混入持久化的 Profile。
- 文件格式必须有 schema version。无效字段不得静默写入硬件；任何外部/旧格式迁移都需要独立定义输入 schema。
- 应用预设是逐项操作，结果必须能表达完全成功、部分成功、失败和跳过原因。自动应用策略可以跳过输入源，但需在结果中可见。

## Linux/Windows 平台能力

- Core 用例不得根据 OS 名称直接分支。通过后端能力表达可用功能及不可用原因。
- DDC/CI、HDR、刷新率、前台应用监测、登录启动和托盘是独立能力，不因 Avalonia 可运行就推断操作系统集成可用。
- Linux DDC/CI 的系统依赖、设备权限和桌面显示会话限制由 Linux adapter/部署文档报告；Core 仅消费结构化能力与结果。

## 本轮稳定流程

1. 对照 `UI-DESIGN.md` 和已确定的产品需求确认数据/操作语义。
2. Core DTO 与接口满足以上规则。
3. App 和 Windows adapter 分别 review 接口可用性，不把平台细节塞进 Core。
4. 冻结 v1 契约后再分派 adapter 与 ViewModel 工作；后续破坏性变更需更新 schema/接口决策并说明迁移影响。

## 审查状态

初始契约审查中发现的回滚责任、预设重复值、错误类别、进度生命周期和探测能力语义已映射到 Core 类型和接口注释。任何既有用户数据迁移都需由用户提供并审查明确的输入 schema；当前 Core 契约不依赖旧实现目录或其代码。

契约 v1 和 Core 刷新率试用协调器已实现并静态审查，解决方案构建通过；新后端实现应对照本文逐项复核。协调器在 UI 关闭后仍由应用服务持有期限任务，用户取消/到期都触发不可取消恢复；应用正常异步退出时会尝试恢复活动试用。进程被强制终止后的自动恢复不在保证范围内。无第三方测试依赖的 C# 契约检查已通过 5 项；Windows UI 启动、显示器发现和能力读取已在当前机器验证，硬件写入仍待验证。
